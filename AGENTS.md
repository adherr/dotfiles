# dotfiles

## Project setup

- `home/` mirrors `$HOME`. `mise run link` (`bin/link`) walks every file in `home/` and symlinks it to the same relative path under `$HOME`. `home/.config/emacs` is a submodule and is linked as a whole directory, not walked file-by-file.
- Two machine roles, recorded per machine in the untracked `~/.config/dotfiles/role` (`bin/role` reads it; scripts refuse to run without it): `full` (my own/employer laptops: everything, multiple clients over time) and `client` (client-owned terminal hosts: only what's needed to work, only that client's config).
- No client-specific config in this repo — no client names, emails, hosts, aliases, or identities. It lives untracked on each machine in the overlay slots the tracked config loads: `~/.gitconfig.local` (includeif blocks → `~/.gitconfig.<client>`), `~/.config/zsh/local.d/*.zsh`, `~/.config/fish/conf.d/*.fish`, `~/.config/mise/conf.d/*.toml` or a per-project `.mise.toml`. It stays on a machine after rolling off and is never synced to a new one.
- No hard-coded home paths (`/Users/<name>`): usernames differ across machines. Use `~`/`$HOME`/`{{env.HOME}}`, or paths relative to the repo. Claude `settings.json` expands `~/` in `additionalDirectories` and sandbox paths but not in `env` values, so home-relative env vars go in `.zshenv`/fish config instead (and in Emacs' `exec-path-from-shell-variables` if Emacs-launched sessions need them).
- `Brewfile` is generated, not hand-edited: after installing/removing a formula or cask on a `full` machine, run `mise run brewfile-dump` (refuses on `client` machines). `Brewfile.client` is the hand-curated subset for `client` machines; keep it a subset of `Brewfile` (the dump task checks).
- New machine bootstrap: `mise run init -- --role full|client`, then `mise run bootstrap` (link, `brew bundle` of the role's Brewfile, `mise install`, role-aware `macos`). Other `mise run` tasks (see `.mise.toml`) are opt-in or individually re-runnable steps.
- macOS app config that needs to live under `~/.config/<app>` (e.g. Karabiner Elements) goes in `home/.config/<app>/` and gets picked up automatically by `bin/link`.
- Respect XDG base dir semantics, not just the letter of `$XDG_*_HOME`: config (`XDG_CONFIG_HOME`) is hand-edited/version-controlled, cache (`XDG_CACHE_HOME`) is regenerable and safe to delete, state (`XDG_STATE_HOME`) is generated but worth keeping (history, logs), data (`XDG_DATA_HOME`) is generated and substantive. When wiring up a new tool's paths, pick the directory that matches what the file actually is, not whichever is closest at hand.
- For live Emacs work (including the `home/.config/emacs` submodule), use `mcp__ide__executeCode`, not `emacsclient`/`emacs --batch` under Bash — the Bash sandbox blocks writes outside its allowlist (e.g. `~/.cache`). Never call `module-load` on a live process just to verify a download; it can crash Emacs. A fresh restart is the only safe way to confirm a native module loads.
- When verifying a change to `init.el` (or any live-loaded elisp) with `mcp__ide__executeCode`, eval only the specific form(s) you changed — never `(load-file ...)` the whole file. Re-running the entire config at runtime re-executes every `use-package`/`load-theme`/`add-hook` form without unwinding the previous run first, which stacks/corrupts live state (themes and faces especially — `load-theme` twice can leave face inheritance cycles that don't clean up with more eval). If you need to confirm the full file loads cleanly end-to-end, that means restarting Emacs, not `load-file`.
